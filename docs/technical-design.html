Technical design document · companion to SRS v3.0

Fifteen days to take an order

Phase 1 is account, catalog, cart, coupon, wallet, Razorpay payment and a delivery window. That is all of it, and it is enough to sell food to a gated community.

This document specifies how it gets built. It is written for the two engineers implementing it and the PMO team planning around it, so it is concrete — schema, endpoints, transactions and sequencing rather than intent. Where this disagrees with the SRS, this governs Phase 1 and the SRS governs everything after.

P1 is settled. It means exactly what was agreed on the technical call. The 185-requirement scope that previously carried the Phase 1 label is now P2 — nothing cancelled, sequence changed.

    The one thing this document cannot solve

    Phase 1 accepts money and has no fulfilment system. Aggregation, procurement, packing, routing and delivery confirmation are all P2. Orders arrive with payment attached and get fulfilled by hand.

    That is a normal way to start a pilot. It is only dangerous if it is accidental. Section 10 specifies the admin screens and CSV exports that make the manual process workable — but it stays a manual process run by a named person, and that person needs agreeing before launch, not after (OQ-36).

    Architecture

    Three deployables and four managed services
    
      
    The API is the only process that touches Postgres. Neither client holds a database credential or a service-role key. Anything shipped to a device is public.

          05
          Authentication
          OTP, rotating tokens, and the serialiser rule
          
      
          Customer — mobile OTP
          
      
            
      
            There is no password anywhere in the customer flow. That removes an entire class of vulnerability and a support burden.
            
      
            Tokens
            
      
            
      
              
      
              The serialiser rule
              
      
              Authorisation is enforced server-side by middleware, never by the client hiding a screen. P1 has two roles, but this is built now because it is far harder to retrofit once P2 adds five more.
              
      
              
      
              Allow-list, never blocklist. A blocklist that deletes forbidden keys silently leaks every new field added later. The accompanying test walks every role and asserts forbidden keys are absent, including nested — and blocks merge on failure.
              
    
              

    
              
      
              06
              The order transaction
              The hardest thing in the build
              
      
              It combines a coupon redemption, a wallet debit, a window decrement and a gateway leg. Any of the four can fail.
              
      
              
      
              Steps 2 to 11 are one database transaction. A partial commit means a customer charged for an order that does not exist, or a coupon consumed with nothing to show for it.
              
      
              When it fails
              
      
              
      
              Wallet top-up
              
      
              
      
              The wallet is credited by the webhook, never by the client telling us the payment succeeded.
              
    
              

    
              
      
              07
              Wallet
              Ledger, locks, closed loop, and the liability nobody tracks
              
      
              Two tables. A wallet row holding the balance for fast reads, and an append-only ledger holding every movement. The ledger is the truth; the balance column is a materialised convenience.
              
      
                
      
                Concurrency
                
      
                Two orders from two devices on the same account must not both spend the same balance. The wallet row is locked with SELECT … FOR UPDATE inside the order transaction, which serialises them.
                
      
                Do not implement this as read-then-write. Write the test first: fifty concurrent orders against a ₹1,000 balance; assert nothing overspends and the ledger reconciles exactly.
                
      
                Closed loop — a constraint, not a preference
                
      
                  
      
                  These rules keep the wallet in the shape that normally sits outside prepaid payment instrument licensing in India. It must be confirmed with a professional before money is accepted — OQ-34, and not an engineering decision.
                  
      
                  Accounting
                  
      
                  
      
                  The last row deserves reading twice. A non-expiring balance is a permanent obligation. A thousand customers each holding ₹400 unused is ₹4 lakh of goods owed indefinitely — against cash already spent on procurement.
                  
    
                  

    
                  
      
                  08
                  Coupons
                  Printed in a brochure, enforced by the database
                  
      
                  
      
                  Five categories with two to three coupons each, per the brochure design. Every redemption traces to a batch and therefore to a channel — which is what turns leaflet spend into a measurable number.
                  
      
                  Rules and where they are enforced
                  
      
                  
      
                  The race nobody tests. A coupon capped at 500 uses, hit by 600 simultaneous redemptions, over-issues if implemented as read-then-increment. Lock the coupon row inside the order transaction. The unique constraint handles per-account reuse; only the global cap needs the lock.
                  
    
                  

    
                  
      
                  09
                  Payments
                  Razorpay, and why the webhook is the only truth
                  
      
                  
      
                  Signature verification
                  
      
                    
      
                    The webhook is the source of truth
                    
      
                    The client tells us a payment succeeded. The client is a device in someone's hand and cannot be trusted. Money moves only when the webhook confirms it.
                    
      
                      
      
                      Reconciliation
                      
      
                      A daily job pulls settled payments from the Razorpay API and matches them against the payment table. Any gateway payment without an internal record, or any internal CAPTURED payment absent from the gateway, is reported. Without this, a webhook outage becomes an accounting problem discovered weeks later.
                      
      
                      Card numbers, CVV, UPI PINs and bank credentials never touch this system. The Razorpay SDK collects them. Use the official React Native SDK, never a WebView wrapper around the checkout page.
                      
    
                      

    
                      
      
                      10
                      Delivery windows and admin
                      Including the screen that replaces the whole P2 operations suite
                      
      
                      Windows in P1
                      
      
                      Fixed windows on configured delivery days. No travel-time feasibility — that needs the routing engine, which is P2.
                      
      
                      
      
                      Window rows are generated fourteen days ahead by a scheduled job, so capacity checks are a single indexed read rather than a computation per request. Capacity decrements under a row lock inside the order transaction, exactly like the wallet.
                      
      
                      Admin panel
                      
      
                      
      
                      The manual fulfilment screen
                      
      
                      This is what stands in for the entire P2 operations suite, and it is the difference between a pilot that works and one that collapses in week one.
                      
      
                        
      
                        Two SQL queries and a CSV writer — perhaps half a day. It removes the need for a spreadsheet maintained by hand alongside the system, which is where pilots usually lose track of what was ordered. The highest-leverage half day in the fifteen.

                            16
                            Extra — new features implemented
                            Built after v1.0 · design changes, fixes and measurements
                            

      
                            Why this section exists. The design above is v1.0. What follows is what the build actually produced afterwards — one design decision reversed, several defects fixed at the source, and the first real load measurements. Where this contradicts a section above, this section is current.
                            

      
                            1 · Window gating: capacity replaced by an IST cut-off clock
                            
      
                            v1.0 gated a delivery window on a per-community windowCapacity with a rolling cutoffHours. That is gone. A community now stores morningCutoff and eveningCutoff as fixed IST times plus cutoffWarningMinutes, and generateWindows() marks a window open purely on whether its cut-off instant has passed. Times are computed through istInstantMs so the boundary is correct regardless of server timezone.
                            
      
                            The cut-off is enforced twice: once when windows are listed, and again inside POST /orders at commit time. The client's earlier isOpen is never trusted — a basket that was legal when checkout opened is rejected with 409 ORDER_CUTOFF_PASSED if the window closed meanwhile, and the error payload carries nextAvailable so the app can re-offer immediately.
                            

      
                            2 · Payment intents no longer advertise a gateway order that does not exist
                            
      
                            The most serious defect found. createPayment() unconditionally stamped a synthetic razorpayOrderId (the mock verify flow keys off it), and both POST /orders and POST /wallet/topup handed that id to the client. With no gateway credentials configured the app opened the payment SDK against an order the gateway had never issued, and the gateway rendered its own failure sheet — checkout was impossible on any environment without live keys.
                            
      
                            Both routes now gate the field on whether a gateway order was actually created:
                            
      
                            razorpayOrderId: razorpayEnabled ? pay.razorpayOrderId : null,
                            
      
                            Note the fix had to be server-side. An earlier client-side guard was a no-op precisely because the server always sent a non-null id.
                            

      
                            3 · Single-pass indexes replace per-line rescans of the order book
                            
      
                            Two hot paths rescanned every order for each item they checked. Both now build one index per request:
                            
      
                            
        
                            AddedReplacesEffect
                            
        
          
                            orderedQtyIndex(deliveryDate)orderedQtyFor() called once per basket lineAn 8-line basket did 8 full scans of the order book at the pre-cut-off peak; now one, then O(1) per line.
                            
          
                            bookedIndex(communityId)bookedFor() called per windowMeasured 7.3× on window generation.
                            
          
                            rawOrders()listOrders() inside the lifecycle sweeperThe 60-second sweeper no longer deep-clones every order; it selects, then patches.
                            
                                    
      
                            
      
                            A measurement worth recording. The first bookedIndex benchmarked at 1.0× — no gain whatsoever. The code it replaced exited on a cheap string comparison, while the index paid for a template-literal key on every order. It was only after scoping the index to a single community (restoring the cheap early-out) that it reached 7.3×. The audit predicted a win; the benchmark disagreed, and the benchmark was right.

                            5 · Staff clients now reconcile with the operator website
                            
      
                            The staff screens in the mobile app fetch through adminApi into local state, with no subscription and no revalidation. Any state the website changed while a screen was open never reached the phone — a procurement buyer who had submitted an over-budget price saw Awaiting admin permanently, including after the admin approved it.
                            
      
                            A shared useStaffRefresh(load) hook now backs every staff screen. It refetches via useFocusEffect whenever the screen regains focus and exposes a RefreshControl for pull-to-refresh; load returns its promise so the spinner ends when data lands. Applied to procurement, orders, fulfilment, console and approvals. It also removed two latent bugs: approvals had refreshing={false} hardcoded so its spinner never appeared, and fulfilment passed a promise-returning load straight to useEffect, where React reads the return value as a cleanup function.

                            7 · What these results do not prove
                            
      
                            Stated explicitly, because the throughput figures above invite the wrong conclusion:
                            
      
                            
        
                            LimitConsequence
                            
        
          
                            Sessions, carts, OTPs and the order-number sequence live in process memoryHorizontal scaling is not safe. More than one replica will issue duplicate order numbers and lose sessions.
                            
          
                            Writes are fire-and-forget over a default Prisma pool (~5)Under a sustained burst a write can be dropped after the response has already succeeded.
                            
          
                            GET /admin/orders is unpaginatedAcceptable at pilot volume, not past it.
                            
          
                            In-memory state grows unboundedNeeds an eviction or restart strategy before a long-running production deployment.
                            
          
                            Gateway signature verification and SMS/WhatsApp OTP deliveryWired but never exercised against a live provider.
