# MobSF static scan — Fooducia 0.2.0 Android

Scanned 8 Oct 2026. **52/100, grade B, Medium Risk.** 2 high, 13 medium, 3 info, 0 trackers.

The headline number is less interesting than the breakdown: of the fifteen high and medium
findings, **three were ours**. The rest are third-party library code that ships in the dex and
never executes, or permissions a dependency declares for itself.

## Fixed

| #   | Finding                                             | Severity | What it actually meant                                                                                                                                                                                                                                         |
| --- | --------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `minSdk=24` — installs on Android 7.0               | high     | Android 7 stopped receiving security patches years ago. Raised to **29** (Android 10).                                                                                                                                                                         |
| 2   | `android:allowBackup=true`                          | medium   | `adb backup` on a USB-debugging device copies the app's private data off the phone. The auth token was already excluded by expo-secure-store's backup rules; the SQLite cache and AsyncStorage were not — cart, saved addresses, order history. Now **false**. |
| 3   | `SYSTEM_ALERT_WINDOW` in the abused-permissions set | —        | Draw-over-other-apps: what a tapjacking overlay needs to sit on top of a payment screen. It came from the Expo bare template, under a comment reading _"REMOVE WHATEVER YOU DO NOT NEED"_. Nothing in this app requests it. **Removed.**                       |

Cleartext HTTP is switched off at the same time (`usesCleartextTraffic="false"`). Every endpoint
is HTTPS today, so it costs nothing now; it means a future `http://` typo fails loudly in
development instead of quietly shipping a customer's address over a cafe's Wi-Fi.

All three are implemented in `apps/customer/plugins/with-android-hardening.js` plus a
`minSdkVersion` in `expo-build-properties`, and verified against a real `expo prebuild`. The
merge-time removal of `SYSTEM_ALERT_WINDOW` can only be confirmed on a full Gradle build.

## Not fixed, deliberately

**Remote WebView debugging enabled** (high, `expo/modules/logbox/ExpoLogBoxWebViewWrapper`).
`@expo/log-box` calls `setWebContentsDebuggingEnabled(true)` unconditionally — verified in
`node_modules/@expo/log-box/android/src/main/.../ExpoLogBoxWebViewWrapper.kt:27`. But the class
is only ever constructed by `ExpoLogBoxDevSupportManager`, and a release build wires up
`ReleaseDevSupportManager` instead, so the constructor never runs. MobSF matches on the presence
of the call in the dex and cannot see reachability. Fixing it means patching an Expo package;
the exposure is nil. **Accepted, with the reasoning recorded here rather than suppressed.**

**`READ_/WRITE_EXTERNAL_STORAGE`.** expo-image-picker declares both itself, capped at
`maxSdkVersion=32`. Removing them breaks photographing a vegetable for the AI lens, or a damaged
delivery, on Android 10–12. Not worth it.

**`com.razorpay.DeeplinkActivity` exported** (medium). Required: it is how the UPI app hands
control back after a payment. Razorpay's own SDK validates the callback; our server never trusts
it — the wallet credit path re-fetches the payment from Razorpay's API and checks the signature
against _our_ stored order id.

**Insecure RNG, clipboard listeners, logging, temp files, insecure WebView** (medium/info). All
in Glide, OkHttp, Expo and the Razorpay SDK. No call site of ours.

**`FORTIFY` not set on 432 shared objects** (medium). Prebuilt `.so` files from React Native and
its dependencies. Not ours to recompile.

**NFC, USE_FINGERPRINT, badge permissions, `READ_BASIC_PHONE_STATE`.** Pulled in by the Razorpay
SDK and the notification-badge shims. Stripping them risks breaking payments on some devices for
no real reduction in attack surface.

## Unrelated finding, higher priority than anything above

`apps/customer/eas.json` sets `EXPO_PUBLIC_RAZORPAY_KEY_ID` to **`rzp_test_…`** in both the
`production` and `preview-live` profiles, while the server now holds live keys. The server would
create a live order and the app would open the test checkout against it. This blocks real
payments and must be set to the live `rzp_live_…` key id before the next build.
